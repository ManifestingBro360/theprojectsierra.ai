We ran four AI coding agents on one repository, with and without coordination

Experiment, 24 November 2026

We gave real coding agents tasks designed to collide, first with plain Git and then with Canopy. The landing gate kept main working every time. Warning agents while they worked barely helped: 1 warned agent in 8 changed its code. This page reports both results.

The setup

A small shop repository: money helpers, a cart, a checkout, and tests. Each agent was a Claude Sonnet model in its own Git worktree and branch, started at the same moment with a brief of a few sentences. No agent was told what the others were doing.

AgentTask
AMake toCents require a second argument, mode
B and DEach add new code that calls toCents, in different files
CFix an unrelated bug

This is the collision Git cannot see. A changes a function's signature. B and D write new calls to the old form in other files. No text conflicts, every branch passes its own tests, and main breaks once they are all merged.

After each run we checked out every state main had been in and ran the tests.

What happened

MeasureResult
Plain Git: states of main that failed their tests1 of 4
With Canopy: states of main that passed, four runs18 of 18
Warned callers who changed their code before landing, runs 1 to 30 of 6
The same, run 4, after contracts were added1 of 2
Landings wrongly refused, run 40

Finding 1: the gate works

Canopy lets main move only through canopy land, which runs the checks on the exact merge commit. A branch written against an old signature is refused, told why, and lands after it merges main and fixes its calls. In four runs nothing broken reached main.

Finding 2: agents ignore warnings

Canopy also tells an agent, mid-task, when a function it calls is changing on another branch. In the first three runs no warned agent acted on it. Making the wording clearer changed nothing.

Looking at the transcripts, ignoring the warning was reasonable. The agent's own copy still had the old function. Its own tests passed. The warning did not say what to write, and the new version was not on main yet. A warning is a request, and the agent had a task.

What we changed

  • Tell the author, not only the callers. The agent making the breaking change is the one that can prevent the collision. Once it was told about new callers, its rework fell from two cycles to one.
  • Contracts. Before a breaking change to shared code can land, its author publishes a test for the new behaviour. Canopy runs it on the old code and accepts it only if a test case fails there. Callers are then shown the new signature and a piece of that test.

In run 4 a caller rewrote its call before landing, after being shown the contract. That was the first time in four runs. The other caller landed before the contract existed and never saw it.

What this does not show

  • Four runs, one small repository, minutes long. One of two is an observation, not a rate.
  • The agents checked in with Canopy by command. Claude Code's hooks, which deliver notices inside each tool call, were not used.
  • A change in what a function returns, with the same signature, was not properly tested and is not caught by contracts.
  • A contract proves the test is real and about the right function. It does not prove the test is good.
  • We wrote the tasks to collide. Real work collides less often.

The open problems

Each of these is an open issue with its current result. Ideas and experiments are as welcome as code.

  • Agents ignore mid-task warnings: 1 of 8 adapted
  • A caller can land before the contract exists
  • Behaviour changes that keep the same signature
  • Two machines cannot see each other's in-flight work
  • Judging whether a contract tests enough
  • Contracts for Python, Go and other test runners
