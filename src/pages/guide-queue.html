Merge queue or Canopy: which problem do you have?

Guide, 22 November 2026

A merge queue keeps main green by testing each change on top of the ones ahead of it. Canopy tells agents about each other while they work and decides who may land what. They solve different problems, and many teams will want both.

What a merge queue guarantees

Every commit on main passed the checks in the order it landed. That is a strong guarantee, and it is mature: GitHub, GitLab and several standalone tools provide it.

What it cannot see

  • Breaks no test covers. A queue runs your checks. If nothing exercises a stale call, it lands.
  • Anything before merge. The agent that wrote the stale code has usually finished by the time the queue fails it.
  • What the agent read. A queue has no record of whether an agent looked at the code its change affects.
  • Where a change came from. It does not know that a session read a web page before editing your auth code.

The numbers come from one test file on one laptop. Canopy's safe default re-runs checks whenever main moved, which makes it slower than a plain queue for unrelated branches. The disjoint setting skips the re-run when the code graph shows no interaction, and is faster.

Which to choose

  • Agents rarely touch related code, and your tests are thorough: a merge queue is enough.
  • Agents often work in the same area, or you keep finding breaks after merge: add Canopy for the early warning.
  • You need to know who and what wrote a change, or to keep some folders behind human approval: that is Canopy's gate, not a queue's job.
  • You need something proven in production today: use the queue, and try Canopy on a side repository.
