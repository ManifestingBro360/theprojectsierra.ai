Catch agent collisions while they work, not at merge.

Canopy is an open-source layer above Git for teams whose code is written by many AI agents at once. It records what each agent reads and writes, tells an agent when another agent’s change breaks what it relies on, and lets main move only through a signed landing gate.

Pull requests were designed for people

People talk before they collide. Agents in separate worktrees do not, and the pull request only finds out afterwards.

Conflicts surface too late

Git sees conflicts in text, at merge. When one agent changes a function’s signature and another writes a new call to it in a different file, both branches pass their own checks and main breaks after both are merged.

The reasoning is gone

A pull request shows the diff. It does not show which of the affected code the agent read, what it never opened, or whether it pulled instructions from a web page along the way.

Rules live in prompts

“Always run the payment tests” in a prompt file is a request. Nothing checks it per folder, and an agent can edit the very file that states the rule.

What it looks like from both sides

An agent hears about a collision as a short note inside its next tool call. You see one verdict per branch, with the reasons.

How Canopy works

Git still stores the code and your forge still hosts it. Canopy watches the work and guards the way into main.

  1. Observe

    Harness hooks report every read, edit and shell command. What a branch wrote is taken from the Git diff, so it cannot be hidden. The agent declares nothing.

  2. Warn

    When a function’s signature changes in one worktree, every other worktree that read it, calls it or depends on it is told in its next tool call. Two agents rewriting the same function are stopped once, then both are told.

  3. Judge

    canopy land works out what changed, what that affects, how much of it the agent read, and what outside content came in. It runs the folder’s checks in a sandbox on the exact merge commit.

  4. Sign

    Each landing is one merge commit with an Ed25519-signed record attached as a Git note. A pre-receive hook on the canonical repository refuses every other route into main.

Rules live in the repository, not in a prompt

One file, read from main and never from the branch being judged. A deeper folder can tighten a rule. Nothing can loosen one.

.canopy/rules.json
{
  "version": 1,
  "rules": [
    { "path": "", "checks": ["npm test"],
      "max_changed_lines": 800 },
    { "path": "src/payments/", "min_coverage": 0.8,
      "no_tainted": true,
      "perf": [{ "cmd": "node bench/charge.js",
                 "max_ms": 200 }] },
    { "path": "src/auth/", "protected": true }
  ]
}
  • Checks run where the agent cannot reachIn a sandbox, on the exact commit that will land. A result reported by a client is never used.
  • An agent has to have lookedmin_coverage is the share of affected code the branch read. Below it, a person decides.
  • Outside content is trackedA branch that read the web or used an MCP tool cannot change no_tainted folders without review.
  • The bar cannot be lowered from insideBuild files, CI, lock files, tests being removed, and the rules file itself all need a person.

What is different

Canopy does not replace your merge queue’s job. It moves the discovery of a conflict from merge time to working time, and it puts the rules somewhere an agent cannot edit them.

Where it stands, and where help is wanted

Canopy is at version 0.1. These are the gaps, stated plainly. Each one is an open issue you can pick up.

Not proven yet

  • No independent security testThe gate and the sandbox have defensive tests. Nobody outside the project has tried to break them.
  • No long run with real agentsReal Claude Code sessions deliver their start-up hooks. Everything past that has been tested with scripted agents only.
  • Sandbox proven on macOS onlyThe Linux sandbox is written and has never been run.
  • One machine is not a security boundaryWhen Canopy and the agents run as the same user, it guards against mistakes, not against a hostile agent.

Good places to start

  • Adapters for other harnessesCodex CLI, Cursor, Gemini CLI, Aider, OpenCode. An adapter sends five kinds of hook event.
  • Run and fix the Linux sandboxA bwrap profile exists. It needs someone with a Linux machine and an afternoon.
  • More languagesJavaScript, TypeScript, Python and Go today. Rust, Java, Ruby and C# need an extractor.
  • Try to break the gateRead SECURITY.md first. Findings are credited in the review log.

New on main, not yet in a release

All of it is off until you switch it on. Tested with scripted agents and stand-in commands only.

  • People, owners and approvalson mainName who owns a folder. A change lands there only when its owners approve the exact commit, and they are asked when a change elsewhere reaches code that depends on theirs.
  • Who and which modelon mainEach landing names the person, the harness and the model. Folders can be limited to models you list. Model names are reported by the harness, so this routes work to a person; it is not proof.
  • A manager agent and vulnerability checkson mainA second opinion from a model you choose, which can only raise the bar, and a lookup of new dependencies in OSV.dev. Not yet run against live models.
  • Environments and notificationson mainStaging and production branches that only move forward, each with its own people and checks. Approvals and alerts go to Slack, Discord or any webhook.
  • Catch-up and other harnesseson mainA returning agent gets one line per function others changed, with the lines to re-read. Codex and hook-less harnesses can connect; the Codex adapter has not been run against Codex.

Questions

Is Canopy a replacement for Git or GitHub?

No. Git still stores the code and your forge still hosts it. Canopy is a layer above them: it records what agents do while they work and decides what may reach main.

How is this different from a merge queue?

A merge queue tests changes one after another at merge time. Canopy tells agents about a conflict while they are still working, before either has committed, and it can block a landing whose new code calls a function that changed on main even when no test covers that call.

How is this different from file locking?

Locks make agents wait whenever their files overlap and miss conflicts between different files. Canopy works at the level of functions and their callers. An agent is made to wait only when two want to rewrite the same function, and only once.

Which coding agents does it work with?

Claude Code is the tested path, through its HTTP hooks. On main there is also a Codex adapter, written from Codex’s documentation and not yet run against Codex, and a check-in command for any harness with no hooks. The landing gate applies the same way to all of them.

Does it work with GitHub.com or GitLab.com?

Partly. Hosted forges do not run custom pre-receive hooks, so there you make the Canopy host the only identity allowed to push to main using branch protection. On a self-hosted Git server the hook enforces it directly.

What does it send off my machine?

Nothing by default. Three optional features reach out when you switch them on: vulnerability lookups send package names and versions to OSV.dev, notifications post to the webhook you give, and a manager agent calls the model you choose. Canopy listens on the loopback address only. It stores file paths, symbol names, hashes and signatures in one SQLite file inside your repository’s .git folder. Tool output is discarded on arrival.

Was Canopy written by AI agents?

Yes, directed by a person. The first version was designed, attacked on paper, built, reviewed and tested by separate Claude agents in defined roles. The review log and the test report are in the repository, including the defects that were found and the security test that did not run.
