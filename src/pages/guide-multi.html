How to run several Claude Code agents on one repository

Guide, 22 November 2026

Give each agent its own Git worktree and branch. That stops them overwriting each other's files. It does not stop them breaking each other's code, and this guide covers both halves.

The setup that works

A worktree is a second checkout of the same repository in another folder, on its own branch. Agents in separate worktrees cannot touch each other's working files.

one worktree per agent
git worktree add ../wt-refunds -b feat/refunds
git worktree add ../wt-cart    -b fix/cart-rounding

# start one Claude Code session in each folder
cd ../wt-refunds && claude
  • One task, one branch, one worktree. Do not let two sessions share a worktree.
  • Keep tasks small enough to land the same day. Long-lived branches drift.
  • Install dependencies per worktree, or use a package manager with a shared store.
  • Remove the worktree when the branch lands: git worktree remove ../wt-refunds.

What still goes wrong

Two agents change the same function

Git reports a text conflict at merge. The second agent has to redo work against code it has never seen. This is the visible failure, and the cheaper one.

One agent changes a function, another calls it

Agent A adds a required argument to total(). Agent B, in another file, writes a new call to the old total(). There is no text conflict. Both branches pass their own tests. After both merge, main is broken. See why a clean merge can still break main.

Nobody knows what an agent looked at

The pull request shows what changed. It does not show whether the agent read the callers of what it changed, or whether it followed instructions it found on a web page.

Rules in a prompt file are requests

A line in CLAUDE.md saying "run the payment tests" depends on the agent choosing to. It can also edit that file.

Without extra tools

  • Split work by folder so agents rarely share code.
  • Use a merge queue so every branch is tested on top of the latest main before it lands.
  • Have each agent run git merge main and the full tests immediately before finishing.
  • Protect build, CI and test configuration with code owners.

This catches most breakage at merge time, as long as a test covers the broken call. The agent that caused it has usually finished by then.

With Canopy

Canopy is an open-source layer above Git that connects to Claude Code through its hooks. It records what each agent reads and writes and tells an agent, inside its next tool call, when another agent changes something it relies on.

in your repository
canopy init      # writes Claude Code hooks and a starter rules file
canopy serve     # the local server and live map
# agents work in worktrees as above, then:
canopy land      # checks, then one signed merge commit on main

In the second failure above, Agent B is told about the changed signature while it is still working, 22 ms after the edit in our test, before either agent has committed. If B never fixes the call, the landing is refused even when no test covers it.

What Canopy does not do yet

  • It has been tested with scripted agents, not at length with real ones.
  • It is proven on macOS only.
  • With its default setting, landing unrelated branches is slower than a plain merge queue.
